🚗 Photo-to-Game-Car Recipe

Description → photos → fitted game asset. The complete pipeline an AI can execute from scratch to turn a one-line car description into a procedural Three.js game car that measurably matches the real car — no Blender, no hand modelling. Proven end-to-end on 2026-11-20 across an 11-car fleet photo harvest and two fully fitted cars.

The tooling

  • gpcar_loft.js — the generic procedural car builder: one continuous multi-station loft body, strip-lofted greenhouse, fascia stacks, working pop-up headlights, wheels. A car is a spec (a JSON data object) fed to buildLoftedCar(spec). Public copies ship inside the worked-example folders below (e.g. the Celica bake-off's copy).
  • fit_car.py — zero-dependency Python 3 CLI (headless Chrome): analyze lays calibrated ruler grids over your photos; verify renders your spec at the photos' angles and stitches side-by-side sheets. It lives with the builder in the gamepress kit (kit/gpcar_loft.js + tools/car-fitter/) — ask the page owner for the kit, or work from a bake-off folder's builder copy plus any headless-Chrome screenshot script.
  • Builder conventions: +Z forward, +Y up, +X driver-left, 1 unit = 1 metre.

Step 0 — Input: the one-line description + canon overrides

You start with exactly this, nothing more:

Year, make, model, trim, colour. Example: “1987 Toyota Celica GT, blue, pop-up headlights, blue headlight beams.”

Before hunting photos, write down the canon overrides — the facts that beat anything the photos show. Photos prove shape; canon decides presentation:

  • Paint — the in-game colour or scheme, even when every reference photo is a different colour. A two-tone fade is specified as endpoints + axis (the Camaro below: white holds from the nose to the windshield line, full maroon by the rear — a front-to-back fade along the car's length, never a top/bottom split).
  • Beam colour — headlight colour is part of the spec from the start (house spec: hero yellow 0xffb800, the Celica's blue 0x0066ff, default warm white 0xffd9a8; lens emissiveIntensity 3.4, front halo cards opacity 0.95 FrontSide only, road pool opacity 0.34, rear untouched). Never ship stock lamps and fix them later.
  • Special states — pop-up headlights (up and down), cop light bar, underglow, T-tops, burnt/wrecked condition. Each changes geometry, so each must be photographed or explicitly described.

If the description and the only available photos disagree on year or generation, that is a decision point for the human — not a detail to smooth over (see Step 1).

Step 1 — Photo hunt: find the angles before touching the tooling

Where to look, in the order that worked

  1. Auction and dealer listings of one single car — Hemmings, Bring a Trailer, Cars & Bids, dealer turntable shoots. A single-car listing shoot is gold: every angle is the same car, same trim, same wheels, often 1920×1280 or better, downloadable from the listing's image CDN.
  2. Wikimedia Commons — good for common cars, provenance recorded free.
  3. Specialist archives as a fallback. If a listing's CDN blocks every download route, record it as a lead in SOURCES.md and move on — do not settle for thumbnails.

Required angle set (the file names the tooling expects)

FileWhy it's required
front34.jpgHero angle; nose taper, fender shoulders, lamp wrap
side.jpgThe money shot: wheelbase, overhangs, beltline, glass rake
rear34.jpgHatch/deck slope, tail panel, rear stance
front.jpgWidth, tumblehome, full front fascia stack
rear.jpgTail-panel segmentation, plate width (your rear ruler)
detail-headlights-up.jpgMandatory if the car has pop-ups: pods up and lit
detail-wheel.jpgSpoke count/style, rim-to-tyre ratio, side markers

Minimum useful resolution: ~1280 px on the long edge. Below that, the ruler grids in Step 2 stop being trustworthy for fascia details.

Provenance discipline — a SOURCES.md in every car's folder

  • Source listing/site, seller, date downloaded, and a per-file table (file → angle → source image ID where the CDN gives one). The exact car photographed: year, trim, mileage, VIN when listed.
  • Trim/generation caveats, stated plainly. Real examples from the fleet harvest: the Celica set is a GT-S standing in for the GT — same T160 shell, so usable, and the SOURCES.md says so. The Mercury Tracer set turned out to be the 1997–99 third generation, not the 1991–96 car in the fleet entry — flagged as an open question for the owner, not silently modelled. The Cavalier set is base trim with unpainted grey bumpers — a painted-bumper model would be the wrong car.
  • One car, one shoot. Never mix angles from different cars or listings into one reference set; a set that mixes cars fits nothing.
  • A wrong-generation or wrong-trim set gets FLAGGED, never silently used.
  • The photos' paint colour is data about the photographed car only. Canon paint (Step 0) always wins.

Step 2 — Analyze: ruler grids and what to measure

python3 fit_car.py analyze \
  --photos /path/to/car-real/my-car \
  --out /path/to/work-dir

Outputs grid-side.png, grid-front.png, grid-rear.png (photos overlaid with 5% minor / 10% major ruler grids) and a starter car-spec.json.

Your rulers — photos have no scale bar, so the car provides two:

  • Wheel/tyre outer diameter — the primary ruler, from the side view. ≈ 0.60–0.64 m for 80s coupes/sedans, 0.68–0.76 m for trucks/SUVs. Measure it in grid units, derive metres-per-unit, and every other measurement follows. The wheel close-up also gives the rim-to-tyre ratio (the Celica fit used 0.68 — measured, not guessed).
  • Licence-plate width — the rear ruler (a US plate is 0.305 m wide). The winning Celica tail panel was measured off plate width.

Measure, in this order:

  1. From the side grid: length, wheelbase, front/rear wheel positions, wheel radius; then trace 7–10 body stations (position, bottom/belt/deck heights) from rear bumper to nose; then the greenhouse trace — windshield rake, roof length and height, B-pillar position, hatch slope. Set z = 0 at the car's midpoint, y = 0 at the tyre ground-contact line.
  2. From the front grid: overall width, per-station widths and crown (tumblehome), and the front fascia stack in vertical order — hood line → grille/lamp band → bumper + rub strip → lower intake → chin spoiler. The stack rhythm matters more than any single part.
  3. From the rear grid: rear widths, tail-panel segmentation (how many lamp sections, where the black centre panel and plate recess sit, where the amber outers end), spoiler, exhaust position.
  4. From the 3/4 views: plan-view nose/tail taper, corner-lamp wrap, fender shoulders, glass tint contrast.

Step 3 — Spec: authoring the car for the loft builder

The spec is one JSON object. The schema is DEFAULT_CAR_SPEC at the top of gpcar_loft.js — every field is commented inline; read it there. Do not expect analyze's starter spec to carry you: it contains dimensions and paint only, so author the full spec against DEFAULT_CAR_SPEC yourself.

  • meta, dims — identity + the Step 2 measurements.
  • paint — colour, clearcoat/roughness, and paint.split for a longitudinal two-tone vertex-colour fade (no textures, no UVs; baked into geometry, survives clearcoat).
  • bodyStations — the loft. This is the silhouette; wheel arches are carved into the loft, never bolted on.
  • greenhouse — glass lofted on the same stations as the body so it never floats or overlaps. Glass spec: rear glass opacity ~0.84–0.88, front/side ~0.52–0.62, darker at the rear; always judge glass with an interior tub behind it. Options include a body-coloured sail pillar and T-tops.
  • frontFascia — grille, corner lamps, lower intake, chin spoiler, and either working pop-ups (both states, with lamp/beam colours) or fixed recessed lamp pockets (the Camaro pattern: quad pockets, painted nose bridge, fog lamps in the grille slot, signals outboard).
  • rearFascia — tail panel (styled variants include a Camaro grid), spoiler/wing, exhaust, mud flaps.
  • trim — side rub strip, rocker skirt, door handles, side markers, hood louvers where the real car has them.
  • wheels — spoke count/style, rim ratio, rim and tyre colours.
⚠️ Trap field: frontFascia.popups.ySurface exists in the schema but is never read by the builder — pod height is sampled from the body stations. A fitting AI can burn a whole verify round on it. Set pod height via the stations at the pod's position.

Step 4 — Verify loop: iterate against the photos

python3 fit_car.py verify \
  --spec /path/to/car-spec.json \
  --photos /path/to/car-real/my-car \
  --out /path/to/out-dir \
  --mode studio

Outputs a render per angle, a side-by-side compare per angle (real photo left, your fit right), and a master compare sheet.

  • Up to 3 rounds. Judge each round at full size against the photos. Round 1 fixes stations/greenhouse; later rounds fix fascia and trim.
  • Judging checklist, in order: (1) side — arches, overhangs, nose height, windshield angle, roof length, hatch slope, tail height. (2) front — fascia stack rhythm; the chin tucks under the bumper (a chin projecting forward as a visible tray lip is the classic miss); pop-up pods sit flush and low, not tall blocks; glass darkness vs the photos. (3) rear — tail-panel segmentation; simplified red blocks are the classic miss.
  • Shared ceilings not to chase: the builder's amber lens material renders pale peach under studio light in every fit; mirrors are builder-black in every fit.
  • The compare panes use object-fit: cover, so pane fill differs between photo and render — judge shape, not frame fill.
  • Expect ~2–5 minutes per verify on a software-GL machine; fully unattended. On a Linux box with no system Chrome, the tool's Chrome lookup only tries macOS app paths and google-chrome/chromium on PATH — a one-line wrapper on PATH pointing at Playwright's headless shell with --no-sandbox fixes it with zero edits to the tool (proven in the second-AI run).

Step 5 — The side-by-side compare: the shipping gate

The verify loop produces the sheet; this step is the formal judgement of it — a gate, not a formality.

  1. Render the matched-angle compare sheet: your fitted car against the real photos at the same six angles (front 3/4 pop-ups down · side profile · rear 3/4 · straight front pop-ups down · straight front pop-ups up & lit · straight rear), in the same harness and lighting for every column.
  2. View it full-size and judge it before anything ships. Nothing integrates — no fleet row, no game — until the sheet has been looked at, full-size, against the Step 4 checklist. A sheet that was generated but never viewed is not a passed gate.
  3. One column per fit. When more than one AI fits the same car, the sheet gains a column per fit — REAL | AI-1 | AI-2 — all rendered through the identical harness, and the scorecard is written angle by angle (who wins the rear, who wins the front, where it's a tie).
  4. The human picks the winner (or the parts of each). Only the winning spec goes on to Step 6.

The three-way Celica sheet — REAL | NEON | MOTH, six matched angles, one harness. Scorecard: rear → Moth (measured tail panel); front → Neon (chin tuck); side + pop-ups → tie.

Step 6 — Game asset: from proof sheet to the fleet

  1. Route the car's row through the loft builder in the shared fleet module. The car's data row carries its spec; every other car's row stays byte-identical.
  2. Keep the fleet interface intact: wheels array, updateWheels(speed, steer, dt) (mind the steer sign convention), a driverAnchor so the seated driver figure sits correctly, and setPopups() where the car has them.
  3. Beams are per-row data, applied by the shared lamp treatment — lens emissive 3.4, FrontSide halo 0.95, road pool 0.34, rear untouched.
  4. Cost note: a loft car is ~170 draw calls / ~14k tris. That's a hero-car budget — the player's car and named crew cars, yes; background traffic, no.
  5. Verify in-game, not just in the viewer: full lineup render with zero errors, plus a capture of the car in the game world with its driver seated, before calling it integrated.

Step 8 — Gotchas (each one cost real time on 2026-11-20)

  • Git connectors corrupt binary files — write paths that take text strings will mangle PNGs. Compare sheets and hero images go up by browser web-upload or stay out of git. Text (specs, code, docs) pushes normally.
  • A push is not proof. After every push, read the file back and compare byte size + a changed string — a stale local snapshot can land the old file while reporting success.
  • A deploy is not live until the served bytes say so. Pages hosting lags minutes, and a single fetch during propagation can return a stale copy — re-fetch before declaring anything “not live”, and verify the served file before declaring it live.
  • Branch is not main. Check which branch a collaborator's push landed on before calling anything shipped.
  • Parallel builders, same file = clobber. Re-base onto the current tip and diff before pushing.
  • A visible anomaly is a stop-and-check, never a footnote — in a compare sheet, in a render, anywhere. If it looks wrong, it is wrong until proven otherwise.

Step 9 — Park it in the mini game

Final step — the recipe isn't done until the car is in the lot.

Every completed fitted car gets added to Fleet Drive, the mini game at Hawk2 games/fleet-drive/ (built on the Bunny Hop world — same street, canal and bridge). The lot is where fitted cars live once they're done: parked in a row, and drivable — walk up, get in, drive it.

  • A car enters the game as one data entry: { name, spec } — the display name plus the exact spec object that passed the Step 5 compare gate. No re-modelling, no second copy of the geometry code: Fleet Drive builds every car in the lot from its spec through the same loft builder.
  • Canon presentation travels with the spec — paint/fade and beam colour are already in it (Steps 0 and 3), so the parked car is the approved car.
  • Adding a car = appending its { name, spec } entry to the lot's car list, then verifying it appears in the row, parked, with beams and pop-up state working — and that it drives.
  • A fitted, gated, fleet-integrated car that never got parked is unfinished work.

Starter prompt — hand this to your AI

Build me a game car from photos using the photo-to-game-car recipe.

THE CAR: <YEAR> <MAKE> <MODEL> <TRIM>, <COLOUR>.
CANON OVERRIDES (these beat the photos): paint = <paint or fade spec>;
headlight beam colour = <hex or "default warm white">;
special states = <pop-ups / light bar / underglow / none>.
